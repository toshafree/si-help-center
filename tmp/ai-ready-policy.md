# Политика AI-ready материалов help center Spread Insight

Версия: 1.0  
Дата: 12 августа 2026 года  
Область действия: публичные материалы help center, предназначенные для поиска, цитирования, пересказа и использования чатами, поисковыми ИИ-системами и программными агентами.

## 1. Назначение политики

AI-ready материал — это материал, который чат или агент может:

1. обнаружить;
2. получить без технических препятствий;
3. правильно разделить на смысловые части;
4. однозначно понять;
5. связать с продуктом, версией и источником;
6. безопасно процитировать;
7. использовать для ответа или выполнения пользовательской задачи.

Эта политика не обещает попадание в ответы конкретной ИИ-системы. Она создаёт условия для корректного retrieval, grounding и цитирования. Базовые SEO-требования из `tmp/seo-policy.md` остаются обязательными: ИИ-поиск в значительной степени использует ту же инфраструктуру обхода, индексирования, канонизации и оценки качества, что и обычный веб-поиск.

В документе используются обозначения:

- **ОБЯЗАТЕЛЬНО** — требование для публикации AI-ready материала.
- **РЕКОМЕНДУЕТСЯ** — стандартное решение, от которого можно отступить с объяснением.
- **ОПЦИОНАЛЬНО** — экспериментальное или дополнительное средство.

## 2. Разделение целей: поиск, действия и обучение моделей

Решение о доступе ИИ принимается отдельно для трёх сценариев:

1. **Поиск и цитирование** — робот индексирует публичные страницы, чтобы включать их в ответы со ссылкой на источник.
2. **Получение по запросу пользователя** — чат или агент открывает конкретную страницу во время выполнения задачи.
3. **Обучение моделей** — контент может использоваться при создании будущих моделей.

Разрешение первого или второго сценария не означает автоматического согласия на третий. Владелец help center ОБЯЗАТЕЛЬНО документирует отдельное решение по обучающим роботам.

Рекомендуемая исходная политика для публичного help center:

- разрешать роботов поиска и пользовательского retrieval;
- отдельно решить, разрешать ли роботов обучения;
- не блокировать обычных поисковых роботов, поскольку ChatGPT, Copilot и другие системы могут использовать внешние поисковые индексы;
- проверять названия и назначение user-agent по официальной документации не реже одного раза в квартал.

## 3. Доступ для AI-роботов

### 3.1. Роботы поиска и retrieval

Если цель — присутствие в ответах и цитатах, ОБЯЗАТЕЛЬНО не блокировать:

- `OAI-SearchBot` — поиск и цитирование в ChatGPT;
- `ChatGPT-User` — получение страницы по явному запросу пользователя ChatGPT; это не поисковый робот, и правила `robots.txt` могут к нему не применяться;
- `Claude-SearchBot` — индексирование для поиска Claude;
- `Claude-User` — получение страницы по запросу пользователя Claude;
- `PerplexityBot` — поиск Perplexity;
- `Perplexity-User` — получение страницы по запросу пользователя Perplexity; провайдер указывает, что такой запрос может не подчиняться `robots.txt`;
- `Googlebot` и `Bingbot` — обычный поиск и системы, использующие их индексы.

Также нужно проверить, что CDN, WAF, bot protection, геоблокировка, rate limiting и JavaScript challenge не возвращают этим роботам `403`, `429` или CAPTCHA вместо статьи.

### 3.2. Роботы обучения

- `GPTBot` относится к возможному использованию материалов для обучения OpenAI.
- `ClaudeBot` относится к возможному использованию материалов для обучения Anthropic.
- Решение разрешить или запретить этих роботов принимает владелец контента совместно с ответственными за право и продукт.
- Запрет обучающего робота не должен случайно блокировать отдельного поискового или пользовательского робота той же компании.

Пример политики «разрешить поиск и retrieval, запретить обучение»:

```txt
User-agent: OAI-SearchBot
Allow: /

User-agent: ChatGPT-User
Allow: /

User-agent: GPTBot
Disallow: /

User-agent: Claude-SearchBot
Allow: /

User-agent: Claude-User
Allow: /

User-agent: ClaudeBot
Disallow: /

User-agent: PerplexityBot
Allow: /

User-agent: Perplexity-User
Allow: /

User-agent: Googlebot
Allow: /

User-agent: Bingbot
Allow: /

Sitemap: https://<основной-домен>/sitemap-index.xml
```

Этот пример применяется только после выбора основного домена. На GitHub Project Pages файл `/si-help-center/robots.txt` не заменяет корневой `/robots.txt` домена `toshafree.github.io`.

## 4. Получаемость и техническая форма

- Основной ответ ОБЯЗАТЕЛЬНО присутствует в серверном или статическом HTML, а не только после выполнения JavaScript.
- Статья доступна по публичному стабильному HTTPS URL с ответом `200`.
- У страницы есть абсолютный canonical, и он совпадает с URL, который нужно цитировать.
- Статья не скрыта за авторизацией, CAPTCHA, обязательным согласием на cookies или интерактивным виджетом.
- Основная информация не должна находиться только внутри iframe, видео, canvas, изображения или загружаемого файла.
- Текст сохраняет правильный порядок чтения при отключённых CSS и JavaScript.
- В HTML корректно указаны `lang`, title, description, H1, заголовки секций, списки, таблицы и ссылки.
- Страница не отдаёт разный по смыслу контент обычному пользователю и роботу.

## 5. Семантическая структура материала

### 5.1. Самодостаточные смысловые блоки

- Каждая H2-секция отвечает на один ясный вопрос или описывает один этап.
- Заголовок секции остаётся понятным без заголовков выше. Вместо `Настройка` используется `Как настроить уведомление о спреде`.
- Первый абзац секции содержит основной тезис, затем доказательства, детали и исключения.
- Местоимения без явного референта минимизируются: вместо `он рассчитывает это` — `калькулятор рассчитывает размер каждой ноги`.
- Секция не зависит от информации, спрятанной только в соседней вкладке или tooltip.
- Ключевые определения и ограничения повторяются там, где без них отдельный извлечённый фрагмент станет неверным. Повтор не должен превращаться в SEO-спам.

### 5.2. Рекомендуемый каркас инструкции

1. **Краткий ответ** — какой результат получится и когда способ применим.
2. **Предварительные условия** — доступ, настройки, данные и версия продукта.
3. **Шаги** — одно проверяемое действие на шаг.
4. **Ожидаемый результат** — что пользователь должен увидеть после важных шагов.
5. **Ограничения и риски** — когда инструкция не подходит или может дать неверный результат.
6. **Типичные ошибки** — симптом, причина и исправление.
7. **Связанные материалы** — следующие действия и определения.

### 5.3. Рекомендуемый каркас объясняющей статьи

1. краткое определение;
2. объяснение простыми словами;
3. точное техническое описание;
4. формула и расшифровка каждой переменной;
5. числовой пример;
6. применение в Spread Insight;
7. допущения, ограничения и источники.

## 6. Прямые ответы и точность

- На вопрос из title/H1 даётся явный ответ в начале страницы.
- Определение формулируется утвердительно: `Фандинг — это…`, а не через длинное вступление.
- В инструкции используются точные названия элементов интерфейса в том же регистре и написании, что в продукте.
- Для каждого числа указываются единица измерения, валюта, знак и временной интервал.
- Относительные даты вроде `сегодня` заменяются абсолютной датой, если материал должен оставаться понятным позднее.
- Версии продукта и условия применимости называются явно.
- Неизвестное, приблизительное и зависящее от биржи помечается как таковое; предположение не выдаётся за факт.
- Примеры отделяются от нормативного поведения и не должны выглядеть как актуальные рыночные данные без даты.
- Материалы о финансах и торговле содержат ограничения метода и не обещают доходность.

## 7. Термины и сущности

- Для каждой важной сущности выбирается одно каноническое название: продукт, инструмент, экран, метрика, стратегия.
- При первом упоминании указываются распространённые синонимы и английский термин: `стандартное отклонение (standard deviation, SD)`.
- Одинаковый термин не используется для разных сущностей без пояснения.
- Названия бирж, контрактов, валют, тикеров и версий записываются последовательно.
- РЕКОМЕНДУЕТСЯ вести единый словарь понятий с отдельным URL для каждого ключевого определения.
- Внутренние ссылки связывают упоминание сущности с её канонической страницей.
- Страница «Что такое Spread Insight» должна однозначно описывать официальное название, назначение, основные возможности, владельца продукта и основной сайт.

## 8. Источники, авторство и доказуемость

Каждый материал ОБЯЗАТЕЛЬНО позволяет определить:

- кто отвечает за содержание;
- когда материал был содержательно проверен;
- для какой версии продукта он актуален;
- какие внешние первичные источники подтверждают изменчивые или спорные факты;
- какой URL является каноническим для цитирования.

Требования к источникам:

- предпочтение отдаётся документации продукта, официальной документации биржи, стандарту, нормативному акту или оригинальной научной работе;
- ссылка ставится рядом с подтверждаемым утверждением, а не в неразмеченном списке в конце;
- анкор объясняет источник: `правила расчёта фандинга Binance`, а не `источник`;
- цитата используется только когда важна точная формулировка; в остальных случаях материал пересказывается с атрибуцией;
- недоступные, перенаправленные и устаревшие источники регулярно проверяются;
- собственные результаты теста помечаются как наблюдение Spread Insight с датой и условиями проверки.

## 9. Метаданные и структурированные данные

### 9.1. Обязательные метаданные

Для каждой статьи должны существовать отдельные поля или вычисляемые значения:

- `title` — конкретный вопрос, задача или понятие;
- `description` — краткий самостоятельный ответ или ожидаемый результат;
- дата публикации, если известна;
- дата последней содержательной проверки;
- автор или ответственная команда;
- редактор/эксперт, если требуется;
- версия продукта или диапазон применимости;
- canonical URL;
- тип материала: инструкция, понятие, обзор, вебинар, release note;
- распространённые aliases для внутреннего поиска и retrieval.

Если текущая схема Starlight не принимает нужные поля, ОБЯЗАТЕЛЬНО сначала расширить content schema, а не хранить метаданные в невалидном frontmatter.

### 9.2. JSON-LD

- Для статей используется подходящий `TechArticle` или `Article`.
- Для навигации используется `BreadcrumbList`.
- Для видео используется `VideoObject`.
- Для реальной пошаговой инструкции может использоваться `HowTo`.
- На уровне сайта описываются `Organization` и `WebSite`.
- Поля JSON-LD совпадают с видимым текстом и canonical URL.
- Даты передаются в ISO 8601, длительность — в ISO 8601 duration, язык указывается явно.
- JSON-LD не заменяет хороший HTML и не содержит факты, отсутствующие на странице.

## 10. Таблицы, формулы, код и данные

- Таблица имеет видимые заголовки и логичную подпись.
- Единица измерения указывается в заголовке столбца или в каждой ячейке.
- Объединённые ячейки используются только при необходимости: простая прямоугольная таблица надёжнее для извлечения.
- Формула сопровождается текстовой записью, определением переменных, единицами и примером вычисления.
- Код и команды находятся в fenced code block с указанием языка.
- В примере явно отделяются ввод, команда и ожидаемый вывод.
- JSON, CSV и другие форматы должны быть синтаксически валидными и копируемыми.
- Скачиваемые данные имеют описание схемы, дату обновления, источник и лицензионные условия.

## 11. Изображения, интерфейс и доступность для агентов

- Смысл изображения передаётся через `alt`, подпись и соседний текст.
- Текст внутри скриншота не считается доступным объяснением и дублируется в статье.
- Указания вида `нажмите синюю кнопку справа` дополняются точным доступным названием элемента.
- Кнопки, вкладки, меню, формы и диалоги имеют корректные HTML-элементы либо ARIA role, name, state и relationship.
- Интерактивный элемент должен быть доступен с клавиатуры и иметь предсказуемое состояние focus.
- Поля формы связаны с label; ошибки сообщаются текстом, а не только цветом.
- Состояние вкладок и раскрывающихся блоков отражается через `aria-selected`, `aria-expanded` и другие подходящие атрибуты.
- У основного контента есть семантические области `header`, `nav`, `main`, `article`, `aside` и `footer` по назначению.
- Автоматическая проверка включает accessibility tree, а не только внешний вид.

Доступная семантическая разметка помогает вспомогательным технологиям и браузерным агентам понимать назначение и состояние интерактивных элементов. Поэтому доступность здесь одновременно является требованием для людей и для агентов.

## 12. Видео и аудио

- Видео никогда не является единственным источником ответа.
- Для каждого ролика публикуются:
  - точное название;
  - краткое резюме;
  - спикеры;
  - дата записи;
  - длительность;
  - текстовая расшифровка либо подробный конспект;
  - главы с временными метками для длинного видео;
  - прямые ссылки на YouTube и Rutube;
  - связанные статьи и определения.
- Расшифровка отделяет речь спикера от редакторских примечаний.
- Автоматическая транскрипция проходит проверку терминов, тикеров, чисел и имён.
- Существенные диаграммы и действия на экране описываются текстом, даже если спикер их не проговаривает.

## 13. Машиночитаемые поверхности

### 13.1. Основные поверхности

ОБЯЗАТЕЛЬНО поддерживать:

- канонический HTML;
- XML sitemap с актуальными canonical URL;
- корректный корневой robots.txt;
- структурированные данные JSON-LD;
- стабильные внутренние ссылки;
- понятные HTTP-коды и редиректы.

### 13.2. Markdown-версии

РЕКОМЕНДУЕТСЯ предоставлять чистую Markdown-версию ключевых материалов, если её можно генерировать из того же источника без расхождения содержимого.

Markdown-версия должна:

- содержать canonical URL исходной HTML-страницы;
- сохранять заголовки, списки, таблицы, код и ссылки;
- исключать меню, декоративные элементы и повторяющийся chrome сайта;
- обновляться атомарно вместе с HTML;
- не создавать отдельную индексируемую копию без canonical или подходящего HTTP-заголовка.

### 13.3. `llms.txt`

РЕКОМЕНДУЕТСЯ опубликовать `/llms.txt` как небольшой курируемый Markdown-указатель:

- официальное название и краткое назначение Spread Insight;
- основной production URL;
- ссылки на стартовые материалы;
- ссылки на обзоры инструментов;
- ссылки на основные понятия и расчёты;
- ссылки на вебинары и release notes;
- контакт или страницу обратной связи;
- короткое описание назначения каждой ссылки.

`llms.txt` является развивающейся договорённостью, а не заменой `robots.txt`, sitemap, canonical или структурированных данных. Его наличие не считается самостоятельным фактором ранжирования и не гарантирует использование конкретным ИИ-провайдером.

Файл ОБЯЗАТЕЛЬНО генерируется или проверяется при сборке, чтобы не содержать удалённых, перенаправленных и неканонических URL. `llms-full.txt` создаётся только при наличии автоматической синхронизации; устаревший полный дамп вреднее его отсутствия.

## 14. Внутренняя архитектура знаний

- Каждая задача пользователя связывается с нужными понятиями и инструментами.
- Обзор инструмента ссылается на отдельные операции; операции возвращают пользователя к обзору и следующему шагу.
- Для похожих сущностей есть явные страницы сравнения, а не только разрозненные упоминания.
- Страница понятия отвечает на вопрос независимо от конкретного экрана, затем показывает применение в продукте.
- Release note ссылается на актуальную инструкцию, а актуальная инструкция при необходимости указывает, с какой версии доступна функция.
- Не создаются разные страницы с противоречащими определениями одного понятия.
- Удаление или объединение материала сопровождается 301 и обновлением sitemap, `llms.txt`, внутренних ссылок и JSON-LD.

## 15. Безопасность и защита от неверного использования

- В статьях не размещаются скрытые инструкции для моделей и агентов, не относящиеся к пользовательскому содержанию.
- Пользовательские комментарии, отзывы и внешние вставки не смешиваются с официальным текстом без явного обозначения.
- Секреты, токены, приватные URL, реальные персональные данные и внутренние системные инструкции не публикуются в примерах.
- Команды, способные изменить или удалить данные, сопровождаются предупреждением, предварительными условиями и способом проверки результата.
- Финансовые примеры не маскируются под актуальные рекомендации и содержат дату, допущения и риски.
- Если агенту нельзя выполнять действие без подтверждения пользователя, это явно написано рядом с шагом.

## 16. Контроль качества и тестирование

### 16.1. Автоматические проверки

Сборка должна проверять:

- наличие обязательных метаданных;
- единственность title, description и canonical;
- корректность HTML heading outline;
- отсутствие битых внутренних и внешних ссылок;
- синтаксис JSON-LD;
- соответствие sitemap и `llms.txt` каноническим страницам;
- отсутствие случайной блокировки поисковых/retrieval-роботов;
- наличие alt, подписей и размеров изображений;
- доступность интерактивных элементов через accessibility tree;
- совпадение HTML- и Markdown-версий по дате и исходной ревизии.

### 16.2. Набор контрольных вопросов

Для каждого важного раздела поддерживается тестовый набор реальных вопросов, например:

- «Что такое фандинг и кто кому платит?»
- «Как найти пару для статистического арбитража?»
- «Как рассчитать размер ног сделки?»
- «Чем криптоскринер отличается от статистического скринера?»
- «Как включить оповещение о достижении уровня спреда?»

После значимого обновления проверяется, что ИИ-система с веб-доступом:

1. находит каноническую страницу;
2. извлекает правильный фрагмент;
3. отвечает без противоречий;
4. указывает условия и риски;
5. ссылается на нужный URL, а не на устаревший redirect;
6. не путает данные разных версий продукта.

Результаты фиксируются как eval: вопрос, ожидаемые тезисы, обязательный источник, недопустимые ошибки и дата проверки.

### 16.3. Тестирование агентами

Для интерактивных сценариев проверяется, что агент может:

- определить назначение кнопки по accessible name;
- открыть поиск и ввести запрос;
- переключить YouTube/Rutube и распознать выбранное состояние;
- пройти навигацию с клавиатуры;
- понять сообщение об ошибке;
- отличить внешнюю ссылку от действия внутри продукта.

## 17. Мониторинг AI-видимости

- Ежемесячно отслеживать referral-трафик с ChatGPT, Perplexity, Copilot и других подтверждённых источников.
- Учитывать только подтверждённые referral- и UTM-параметры: провайдеры могут менять их или не передавать вовсе.
- Проверять server/CDN-логи на успешные ответы и ошибки для AI user-agent.
- Отслеживать, какие страницы цитируются, по каким вопросам и с какими фактическими ошибками.
- Ошибочный ответ рассматривается как сигнал проверить неоднозначность текста, канонизацию, устаревшие копии, источники и структуру фрагмента — а не как повод добавлять скрытые инструкции для модели.
- Не реже раза в квартал пересматривать официальный список AI-роботов и назначение каждого user-agent.
- Изменения `llms.txt`, schema или robots оцениваются экспериментально; нельзя объявлять их эффективными без измеримых данных.

## 18. Definition of Done для AI-ready страницы

Материал считается AI-ready, если:

- [ ] доступен публично с `200 OK` и содержательным статическим HTML;
- [ ] имеет один canonical URL на основном домене;
- [ ] разрешён для выбранных поисковых и retrieval-роботов;
- [ ] в начале содержит прямой ответ или ожидаемый результат;
- [ ] разбит на самодостаточные секции с описательными H2/H3;
- [ ] использует однозначные термины, версии, даты и единицы измерения;
- [ ] содержит автора/владельца, дату проверки и источники;
- [ ] включает ограничения, риски и условия применимости;
- [ ] изображения и интерфейс имеют текстовое и доступное описание;
- [ ] видео дополнено резюме или проверенной расшифровкой;
- [ ] имеет корректные JSON-LD и внутренние связи;
- [ ] включён в sitemap и, если применимо, в `llms.txt`;
- [ ] проходит контрольные вопросы и тест на корректное цитирование;
- [ ] не содержит секретов, скрытых model-инструкций и противоречий с другими страницами.

## 19. Приоритет внедрения для текущего репозитория

### P0 — доступ и однозначность

1. Выбрать основной домен и canonical для всех страниц.
2. Решить проблему корневого `robots.txt`, связанную с GitHub Project Pages.
3. Явно утвердить политику search/retrieval и отдельную политику обучения.
4. Разрешить нужных AI-роботов на уровне robots, CDN и WAF.
5. Переписать описания, состоящие только из раздела и времени чтения, в самостоятельные ответы.
6. Устранить устаревшие индексируемые копии и цепочки редиректов.

### P1 — качество знаний

1. Ввести обязательные поля автора, редактора, даты проверки и версии продукта.
2. Добавить прямые ответы в начало существующих статей.
3. Привести заголовки секций к самодостаточной форме.
4. Опубликовать расшифровки или подробные конспекты видео и вебинаров.
5. Внедрить JSON-LD для организации, статей, хлебных крошек и видео.
6. Создать и поддерживать словарь канонических терминов.

### P2 — специальные AI-поверхности и evals

1. Генерировать `/llms.txt` из проверенного списка канонических материалов.
2. Добавить синхронизированные Markdown-версии ключевых страниц.
3. Создать набор контрольных вопросов и автоматизированный retrieval/citation eval.
4. Проверять основные интерактивные сценарии через accessibility tree и браузерного агента.
5. Настроить отчёт по AI referral, цитируемым страницам и ошибкам crawler-доступа.
