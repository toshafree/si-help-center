# Политика SEO-оптимизации help center Spread Insight

Версия: 1.0  
Дата: 12 августа 2026 года  
Область действия: все публичные страницы help center, включая статьи, вебинары, страницы обновлений, изображения, видео и служебные файлы.

## 1. Назначение политики

Цель политики — сделать материалы help center доступными для обхода, понятными поисковым системам, полезными пользователям и конкурентоспособными в органической выдаче.

Выполнение требований не гарантирует конкретную позицию или попадание страницы в индекс. Поисковые системы прямо указывают, что техническая корректность лишь создаёт условия для индексирования и ранжирования. Основным фактором остаётся полезный, достоверный и оригинальный материал, соответствующий намерению пользователя.

В документе используются обозначения:

- **ОБЯЗАТЕЛЬНО** — требование блокирует публикацию или требует исправления в ближайшем релизе.
- **РЕКОМЕНДУЕТСЯ** — требование выполняется по умолчанию; отклонение должно иметь объяснение.
- **ОПЦИОНАЛЬНО** — улучшение, которое внедряется после обязательных требований.

## 2. Целевые результаты

Help center должен:

1. Отдаваться поисковому роботу как полноценный статический HTML без обязательного выполнения JavaScript.
2. Иметь один однозначный канонический URL для каждого материала.
3. Быть доступным через логичную структуру ссылок и XML sitemap.
4. Давать полный, точный и проверяемый ответ на конкретную задачу пользователя.
5. Быстро загружаться, корректно работать на мобильных устройствах и быть доступным для вспомогательных технологий.
6. Содержать актуальные сведения о продукте, авторстве, источниках и дате проверки.
7. Измеряться через Google Search Console, Bing Webmaster Tools и продуктовую аналитику.

## 3. Основной домен и канонизация

### 3.1. Единый основной адрес

- ОБЯЗАТЕЛЬНО выбрать один публичный адрес help center как основной. Предпочтительный вариант — собственный поддомен Spread Insight, например `help.<домен-продукта>`.
- ОБЯЗАТЕЛЬНО использовать основной адрес в `site`, canonical URL, sitemap, Open Graph, внутренних ссылках и внешних ссылках на документацию.
- ОБЯЗАТЕЛЬНО настроить постоянные серверные редиректы `301` со всех прежних адресов на соответствующие новые страницы.
- Если один и тот же контент остаётся доступен на GitHub Pages и другом хостинге, ОБЯЗАТЕЛЬНО указать на обеих копиях canonical на основной адрес. Предпочтительнее закрыть или перенаправить вторую копию.
- Нельзя одновременно считать основными `toshafree.github.io/si-help-center/` и домен `*.chatgpt.site`.

### 3.2. Ограничение GitHub Project Pages

Стандартный файл `robots.txt` запрашивается только из корня origin, например `https://toshafree.github.io/robots.txt`. Файл по адресу `/si-help-center/robots.txt` не является robots-файлом для этого origin.

Поэтому для полноценного управления поисковыми и AI-роботами ОБЯЗАТЕЛЬНО выполнить одно из условий:

1. подключить собственный домен к help center;
2. управлять корневым сайтом `toshafree.github.io` и разместить robots-файл там;
3. до миграции вручную отправлять sitemap в панели поисковиков и управлять индексированием на уровне страниц, принимая ограничение robots.txt.

## 4. Обход и индексирование

### 4.1. Доступность контента

- Каждая индексируемая статья ОБЯЗАТЕЛЬНО возвращает `200 OK` и содержит основной текст в исходном HTML.
- Основной текст, заголовки и ссылки нельзя загружать только после выполнения JavaScript.
- Страница не должна требовать авторизацию, CAPTCHA, cookie consent или действие пользователя для чтения основного материала.
- CSS, JavaScript, изображения и шрифты, необходимые для корректного отображения страницы, не должны блокироваться для поисковых роботов.
- Публичные страницы не должны содержать `noindex`, `nofollow` или `X-Robots-Tag: noindex`, если исключение не согласовано отдельно.

### 4.2. Коды ответа

- Существующая страница возвращает `200`.
- Перенесённая страница возвращает `301` непосредственно на конечный URL, без цепочки редиректов.
- Удалённая без замены страница возвращает `410` или корректный `404`.
- Страница ошибки не должна возвращать `200` — мягкие 404 запрещены.
- Внутренние ссылки на `3xx`, `4xx` и `5xx` исправляются до публикации.

### 4.3. Sitemap

- ОБЯЗАТЕЛЬНО публиковать XML sitemap или sitemap index после каждой production-сборки.
- Sitemap содержит только канонические, индексируемые URL с ответом `200`.
- В sitemap нельзя включать редиректы, 404, служебные страницы, дубликаты и URL с `noindex`.
- URL указываются абсолютными, включая протокол и основной домен.
- `lastmod` меняется только при содержательном обновлении страницы, а не при каждой сборке.
- Sitemap ОБЯЗАТЕЛЬНО отправить в Google Search Console и Bing Webmaster Tools.
- При наличии корректного корневого `robots.txt` в нём указывается абсолютная ссылка `Sitemap:`.

### 4.4. Robots

- `robots.txt` управляет обходом, но не используется как средство удаления страницы из индекса.
- Для исключения HTML-страницы применяется `noindex` при сохранённом доступе робота к странице либо авторизация.
- Production и preview-среды должны иметь разные правила. Preview, тестовые и временные копии ОБЯЗАТЕЛЬНО закрываются от индексирования.
- Изменения правил robots проходят ручную проверку: случайный `Disallow: /` считается критической ошибкой.

## 5. URL и структура сайта

- URL ОБЯЗАТЕЛЬНО короткий, стабильный, в нижнем регистре, с дефисами между словами.
- URL отражает тему и место статьи в структуре: `/tools/stat-screener/backtester/`.
- В URL не используются случайные идентификаторы, UTM-метки, пробелы, подчёркивания и параметры для основной версии страницы.
- Дата включается в URL только когда она является частью сущности, например в странице релиза.
- Переименование заголовка не требует автоматического изменения стабильного URL.
- При переносе материала старый URL сохраняет постоянный редирект на наиболее близкую по смыслу страницу.
- Для каждой страницы существует только один вариант со слешем или без него; второй вариант перенаправляется на канонический.

## 6. Метаданные страницы

Каждая индексируемая страница ОБЯЗАТЕЛЬНО содержит:

- уникальный HTML `<title>`;
- уникальное содержательное `meta name="description"`;
- абсолютный `link rel="canonical"`;
- один видимый `h1`;
- корректный `html lang="ru"`;
- Open Graph title, description, URL и изображение, если для страницы есть подходящая обложка;
- favicon и название сайта.

### 6.1. Title

- Title кратко и точно называет задачу или понятие страницы.
- Главная формулировка ставится в начало, бренд — в конец: `Как настроить оповещения о спреде | Spread Insight`.
- Title не должен состоять только из названия раздела или повторяться на разных страницах.
- Не используются кликбейт, необоснованные обещания, набор синонимов и повтор ключевых слов.
- H1 и title могут различаться, но должны описывать один и тот же материал.

### 6.2. Description

- Description в одном-двух предложениях сообщает, что пользователь узнает или сделает на странице.
- Ориентир — примерно 120–160 символов, но смысл важнее фиксированной длины.
- Строки вида `Инструменты · Статистический скринер · 5 мин` не являются достаточным SEO-описанием. Метаданные раздела и времени чтения хранятся отдельно.
- Description должен быть написан для человека и не содержать перечень ключевых слов.

### 6.3. Заголовок H1

- На странице используется ровно один смысловой H1.
- H1 формулируется так, чтобы вне контекста меню было понятно, о чём материал.
- Названия вроде `Обзор`, `Возможности` или `Настройка` дополняются объектом: `Обзор статистического скринера`.

## 7. Требования к содержанию статьи

### 7.1. Соответствие намерению пользователя

- Одна статья решает одну основную задачу или полно раскрывает одно понятие.
- В первых двух-четырёх предложениях даётся прямой ответ: что это, зачем нужно или какой результат получит пользователь.
- Для инструкции в начале указываются результат и необходимые условия.
- Для сложной темы объясняется связь с рабочим процессом Spread Insight.
- Статья должна быть полезна без просмотра видео; видео дополняет, а не заменяет текст.

### 7.2. Полнота и структура

Инструкция по возможности включает:

1. краткий ответ или ожидаемый результат;
2. предварительные условия;
3. последовательные шаги;
4. ожидаемое состояние после ключевых действий;
5. ограничения, риски и типичные ошибки;
6. практический пример;
7. блок «Что дальше» со связанными материалами.

Теоретическая статья по возможности включает:

1. определение;
2. простое объяснение механизма;
3. формулу с расшифровкой переменных, если применимо;
4. числовой пример;
5. применение в Spread Insight;
6. ограничения и источники.

### 7.3. Качество и доверие

- Факты ОБЯЗАТЕЛЬНО проверяются по первичным источникам: документации бирж, спецификациям, научным публикациям или данным продукта.
- Заимствованный материал пересказывается своими словами и получает ссылку на источник.
- Точные числа, комиссии, расписания, лимиты и характеристики сопровождаются датой актуальности и источником.
- Важные страницы содержат автора или ответственного редактора, дату последней содержательной проверки и применимую версию продукта.
- Материалы о торговле и расчётах явно отделяют описание инструмента от инвестиционной рекомендации и содержат необходимое предупреждение о рисках.
- Автоматически сгенерированный текст нельзя публиковать без фактической и редакторской проверки человеком.

### 7.4. Язык

- Текст написан естественным русским языком, без искусственного повторения запросов.
- При первом упоминании термина указывается основной русский вариант и распространённый английский эквивалент: `фандинг (funding)`.
- Терминология едина во всём help center. Для синонимов выбирается каноническое название.
- Орфография, пунктуация, единицы измерения и формат чисел единообразны.

## 8. Заголовки, списки и таблицы

- Иерархия идёт последовательно: H1 → H2 → H3; уровни не выбираются ради визуального размера.
- Заголовок описывает содержание секции и остаётся понятным отдельно от статьи.
- Для процедур используются нумерованные списки, для наборов — маркированные.
- Таблицы применяются только для реального сравнения или точного соответствия полей.
- У таблицы есть заголовки строк или столбцов; значение каждой ячейки понятно из контекста.
- Длинные абзацы разбиваются по смыслу. Нельзя дробить текст на множество однофразных SEO-секций без пользы читателю.

## 9. Внутренняя перелинковка

- У каждой индексируемой статьи есть хотя бы одна входящая ссылка с другой индексируемой страницы.
- Статья доступна от главной не более чем за три осмысленных перехода.
- Ссылки в тексте используют описательный анкор: `настройка оповещений`, а не `здесь`.
- Ссылка ведёт на страницу, которая продолжает текущую задачу, объясняет термин или подтверждает источник.
- Важные тематические страницы объединяются в кластеры: обзор инструмента → настройка → проверка → расчёт → связанные понятия.
- Хлебные крошки должны отражать каноническую иерархию, даже если левое меню визуально ограничено двумя уровнями.
- Страницы без входящих ссылок и тупиковые страницы выявляются автоматической проверкой.

## 10. Изображения и видео

### 10.1. Изображения

- Информативное изображение имеет краткий содержательный `alt`; декоративное — пустой `alt=""`.
- Важная информация не существует только внутри изображения: она дублируется текстом.
- Файлы имеют понятные имена, корректные размеры, заданные `width` и `height` и современный формат там, где это возможно.
- Изображения ниже первого экрана загружаются лениво.
- Скриншот сопровождается подписью или соседним текстом, который объясняет, что на нём нужно увидеть.
- Устаревший интерфейс на скриншоте считается содержательной ошибкой статьи.

### 10.2. Видео

- У каждого видео есть название, краткое описание, рабочая миниатюра, длительность и дата публикации, если она известна.
- Страница содержит текстовое резюме или полную расшифровку ключевого содержания.
- Для длинных видео добавляются главы с временными метками.
- Переключатель YouTube/Rutube не должен скрывать от робота заголовок, описание и прямые ссылки на обе платформы.
- Для страниц, где видео является существенной частью материала, РЕКОМЕНДУЕТСЯ `VideoObject` с реальными значениями `name`, `description`, `thumbnailUrl`, `uploadDate`, `duration` и URL просмотра или встраивания.

## 11. Структурированные данные

- Структурированные данные добавляются в JSON-LD и всегда совпадают с видимым содержанием страницы.
- На уровне сайта РЕКОМЕНДУЕТСЯ описать `Organization` и `WebSite`.
- На статьях РЕКОМЕНДУЕТСЯ использовать подходящий тип `TechArticle` или `Article` с headline, description, datePublished, dateModified, author, publisher и canonical URL.
- Для навигации РЕКОМЕНДУЕТСЯ `BreadcrumbList`.
- `HowTo` используется только для реальной пошаговой инструкции; `VideoObject` — только для реально присутствующего видео.
- Нельзя размечать скрытый, выдуманный или отсутствующий на странице контент.
- После изменения схемы ОБЯЗАТЕЛЬНО запускать Schema Markup Validator и, для поддерживаемых типов, Google Rich Results Test.
- Наличие корректной разметки не гарантирует расширенный результат и само по себе не повышает позицию.

## 12. Производительность и удобство страницы

- Сайт работает только по HTTPS и не содержит mixed content.
- На мобильных устройствах доступен тот же основной материал, что и на десктопе.
- В полевых данных на 75-м перцентиле целевые значения Core Web Vitals:
  - LCP ≤ 2,5 секунды;
  - INP ≤ 200 миллисекунд;
  - CLS ≤ 0,1.
- Шрифты, стили и скрипты не должны неоправданно блокировать первый рендер.
- Изображения и видео не должны вызывать скачки макета.
- Нельзя использовать навязчивые межстраничные окна, перекрывающие основной материал.
- Основная навигация, поиск, видео-переключатель и интерактивные элементы работают с клавиатуры и имеют доступные имена.
- Контраст, размер шрифта и длина строки обеспечивают комфортное чтение.

## 13. Обновление и жизненный цикл материалов

- Для каждой статьи назначается владелец или ответственная команда.
- Материалы о текущем интерфейсе проверяются после каждого существенного релиза продукта.
- Понятия и расчёты проверяются не реже одного раза в год; страницы с комиссиями, лимитами и расписаниями — чаще, исходя из изменчивости данных.
- `dateModified` и `lastmod` меняются только после содержательной проверки или изменения.
- Устаревшая статья обновляется, объединяется с более сильной страницей через 301 или удаляется с корректным 410. Сохранять заведомо неверный текст ради трафика запрещено.
- Страницы релизов остаются историческими и явно указывают версию и дату, чтобы их не путали с текущей инструкцией.

## 14. Публикационный контроль

### 14.1. Автоматические проверки в CI

Production-сборка ОБЯЗАТЕЛЬНО завершается ошибкой при следующих нарушениях:

- отсутствуют title, description, canonical или H1;
- title или description полностью дублируется у нескольких индексируемых страниц;
- найдено более одного H1;
- внутренняя ссылка ведёт на несуществующую страницу;
- canonical указывает на неуспешный, неосновной или незащищённый URL;
- sitemap содержит редирект, 404, `noindex` или неканонический URL;
- у информативного изображения отсутствует alt;
- структурированные данные не проходят синтаксическую проверку;
- production-сайт случайно закрыт от индексирования.

РЕКОМЕНДУЕТСЯ также контролировать Lighthouse SEO, accessibility и performance, размер клиентского JavaScript и Core Web Vitals на ключевых шаблонах.

### 14.2. Редакторская проверка

Перед публикацией редактор подтверждает:

- статья отвечает на заявленный вопрос;
- первые абзацы дают прямой ответ;
- шаги проверены в актуальной версии продукта;
- факты и числа имеют источник;
- иллюстрации актуальны и понятны;
- связанные статьи и следующий шаг указаны;
- заголовок и description полезны пользователю, а не только содержат ключевые слова.

## 15. Мониторинг

- ОБЯЗАТЕЛЬНО подтвердить основной домен в Google Search Console и Bing Webmaster Tools.
- После запуска или миграции проверить главную, по одной странице каждого шаблона и самые важные статьи через URL Inspection.
- Еженедельно отслеживать критические ошибки индексирования, sitemap, ручные меры и проблемы Core Web Vitals.
- Ежемесячно анализировать:
  - индексируемые и исключённые страницы;
  - показы, клики, CTR и поисковые запросы;
  - страницы с ростом и падением трафика;
  - запросы с показами, но низким CTR;
  - страницы без органических показов;
  - битые ссылки и ошибки ответа;
  - органические входы, внутренний поиск и успешность перехода к продукту.
- Изменения оцениваются по тренду минимум за несколько недель, а не по позиции в отдельный день.
- Для новых и существенно обновлённых страниц РЕКОМЕНДУЕТСЯ использовать IndexNow для ускорения обнаружения Bing и поддерживающими протокол системами.

## 16. Запрещённые практики

Запрещено:

- набивать текст повторяющимися ключевыми словами;
- создавать десятки почти одинаковых страниц под варианты одного запроса;
- скрывать текст от пользователя, но показывать его роботу;
- покупать или массово обменивать ссылки ради манипуляции рейтингом;
- копировать чужие статьи без самостоятельной ценности;
- публиковать непроверенный массово сгенерированный контент;
- менять дату без реального обновления;
- размечать структурированными данными отсутствующий контент;
- обещать гарантированную доходность или выдавать обучающий материал за персональную инвестиционную рекомендацию;
- использовать `meta keywords`: Google не использует этот тег для ранжирования.

## 17. Definition of Done для индексируемой страницы

Страница считается готовой, если одновременно выполнено следующее:

- [ ] возвращает `200` и содержит основной материал в HTML;
- [ ] имеет один основной URL и self-canonical на production-домене;
- [ ] присутствует в актуальном sitemap;
- [ ] имеет уникальные title, description и H1;
- [ ] даёт прямой ответ в начале;
- [ ] содержит проверенные шаги, пример или полноценное объяснение;
- [ ] указывает владельца/автора, дату проверки и версию продукта, где это важно;
- [ ] содержит корректные внутренние ссылки и хотя бы одну входящую ссылку;
- [ ] изображения имеют alt и фиксированные размеры;
- [ ] видео дополнено текстом и метаданными;
- [ ] работает на мобильном экране и с клавиатуры;
- [ ] не содержит битых ссылок, ошибок schema и случайных запретов индексирования;
- [ ] прошла редакторскую и техническую проверку.

## 18. Приоритет внедрения для текущего репозитория

### P0 — до активного SEO-продвижения

1. Выбрать единственный production-домен и устранить конкурирующие копии.
2. Обеспечить абсолютный canonical для всех страниц.
3. Решить размещение корневого `robots.txt`; предпочтительно перейти на собственный домен.
4. Проверить production sitemap и отправить его в Google Search Console и Bing Webmaster Tools.
5. Переписать frontmatter `description`, где сейчас указаны только раздел и время чтения.
6. Проверить, что legacy URL отдают настоящие 301, а не индексируемые HTML-заглушки.

### P1 — следующий этап

1. Добавить автора/редактора, дату содержательной проверки и версию продукта.
2. Добавить JSON-LD для организации, хлебных крошек, статей и видео.
3. Подготовить текстовые резюме или расшифровки всех видео.
4. Автоматизировать проверки метаданных, ссылок, sitemap и изображений.
5. Настроить мониторинг Search Console, Bing Webmaster Tools и Core Web Vitals.

### P2 — развитие

1. Создавать тематические кластеры на основе реальных запросов и данных внутреннего поиска.
2. Добавлять оригинальные примеры, исследования, сравнения и практические сценарии.
3. Внедрить IndexNow и автоматический аудит после публикации.
4. Планово улучшать сниппеты страниц с показами и низким CTR.
